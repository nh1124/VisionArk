# マルチクライアント・アクセス高速化のための並列処理調査レポート

## 1. 現状の実装
現在の VisionArk のシステムアーキテクチャでは、クライアント（フロントエンド）からのリクエスト処理とバックグラウンドタスク（Worker）の実行において、以下の仕組みが採用されています。

### バックエンド (FastAPI / main.py)
- **FastAPI + Uvicorn**: 非同期（asyncio）ベースで動作しており、I/O 待ちの間は他のリクエストを受け付けることができます。
- **シングルプロセス実行**: 現在の起動スクリプトでは、単一の Uvicorn プロセスで動作しています。

### ワーカー (Worker / worker.py)
- **逐次処理**: `while True` ループ内で Redis キューから1つずつタスクをデキュー（`blpop`）し、そのタスクが完了するのを `await` で待機してから次のタスクを処理しています。
- **非同期 I/O**: 各タスク内部のリサーチや LLM 呼び出しは `async` ですが、Worker 本体のメインループが同期的にタスクを1つずつしか回さないため、実質的に並列実行は行われていません。

### キュー・DB
- **Redis**: タスクのキューイングに使用されています。
- **SQLAlchemy (Async)**: 非同期セッションを使用して DB 操作を行っています。

## 2. マルチスレッド（並列処理）のための問題点
現状のまま並列化を進める上で、以下の課題があります。

1. **Worker の逐次実行ボトルネック**:
   - `_process_task` が完了するまで次の `dequeue` が行われないため、複数のユーザーが同時にタスクを投げても、前のタスクが終わるまで待たされます。
2. **同期 Redis クライアントの使用**:
   - `QueueManager` が同期版の `redis-py` を使用しており、`run_in_executor` でラップしていますが、多重実行時には非効率になる可能性があります。
3. **共有リソースの競合**:
   - シングルトンである `QueueManager` や、ファイルシステムへの書き込み（ログ、成果物保存）において、適切な排他制御やディレクトリ分離が行われていないと、書き込み競合が発生するリスクがあります。
4. **Python の GIL (Global Interpreter Lock)**:
   - スレッドのみの並列化では、CPU バウンドな処理（ローカルでのデータ解析など）において性能向上が限定的です。I/O バウンドな処理（LLM API 等）についてはスレッド/非同期で解決可能です。

---

## 3. マルチスレッド（並列実行）のための提案

### A. Worker の並列度向上 (Async Concurrency)
Worker のメインループを改良し、タスクをフェッチしたらすぐに `asyncio.create_task()` でバックグラウンド実行するように変更します。
- `asyncio.Semaphore` を使用して、同時に実行する最大タスク数（スレッド数に相当）を制限し、リソースの枯渇を防ぎます。

### B. マルチプロセス化 (Scaling Out)
OS レベルで複数の Worker プロセスを立ち上げます。
- Redis の `BLPOP` はアトミックであるため、複数のプロセスが同じキューを監視してもタスクの二重取りは発生しません。これにより、複数コアをフル活用できます。

### C. 非同期 Redis クライアントへの移行
`QueueManager` を `redis.asyncio` (旧 aioredis) に切り替え、完全な非同期 I/O を実現します。これにより、タスクのフェッチ待ち自体も軽量化されます。

### D. バックエンドのワーカー数増加
`uvicorn` の起動引数に `--workers [N]` を追加し、API 受付側の並列処理能力を向上させます。
