# ツール応答不全により「計画のみ」が返却された事象の分析レポート

- 作成日: 2026-02-14
- 対象事象: 添付資料を使った原稿作成依頼に対し、実行計画のみが返却され、本文生成に進まなかった
- 観測ログ: `list_files` / `list_notes` が `Success` を返す一方で `No response received` が継続

## 1. 事象サマリ

今回の実行では、エージェントは最初に妥当な実行計画（資料列挙→資料読込→原稿化）を提示しました。しかし、その後の実ツール呼び出しで **列挙 API が空レスポンス状態** となり、添付ファイル本文に到達できませんでした。

結果として、計画段階から本文生成段階へ遷移できず、期待された「Phase 1 / 中西様担当パートの発表原稿」は返却されませんでした。

## 2. ログから読み取れる事実

提示ログの時系列上、以下が確認できます。

1. `list_files` / `list_notes` 自体は `Success` と判定される。
2. ただし毎回 `No response received` が返る。
3. 次ステップに `[dir] refs/` のみが出力され、ファイル一覧（`.pptx` / `.pdf` / `.docx` 等）が展開されない。
4. 同一引数 (`refs/`, `artifacts/`) で多数回リトライしても変化なし。

このパターンは、**「ツール呼び出し成功」=「RPC の受付成功」だが、「実データのペイロード返却」は失敗** している状態と整合します。

## 3. 「ツール不具合を確認できたか」への回答

### 3.1 現時点で確認できたこと

- 提示ログだけでも、ツール経路に異常があることは高い確度で確認できます。
- 根拠は、`Success` と `No response received` が同時に出ており、かつ再試行で同一現象が反復している点です。
- これは「モデルが内容生成を拒否した」のではなく、「入力資料を取得できないため生成に進めない」状態を示します。

### 3.2 まだ確認できていないこと

- どの層で壊れているか（クライアントUI / ツールブリッジ / バックエンドAPI）は、提示ログのみでは断定できません。
- 429/5xx、タイムアウト、デコード失敗などの**一次エラーコード**が不足しており、最終原因の特定にはサーバー側ログ（request_id紐付け）が必要です。

### 3.3 結論（確認レベル）

- **ツール不具合の存在: 確認済み（高確度）**
- **不具合箇所の特定: 未確認（追加ログが必要）**

## 4. 原因分析（可能性の高い順）

### A. ツールブリッジ層の応答欠落（最有力）

`Success` と `No response received` の同居は、実行管理層が「呼び出し自体は完了」とみなした一方、
- 標準出力の収集失敗
- JSON ボディの破棄
- ストリーム終端の検知不全

などで結果本文を受け取れなかった可能性を示します。

### B. 仮想ファイルシステム側のメタデータのみ返却

`[dir] refs/` は返るため、ルート存在確認までは通っています。逆に言えば、
- ディレクトリメタ情報のみ取得できる
- 配下列挙・本文取得に必要な権限/マウントが欠けている

という部分断裂（partial availability）の可能性があります。

### C. レート制限・タイムアウト後のラッパー誤変換

内部でタイムアウトや 429/5xx が発生しても、上位 UI がそれを統一文言 `No response received` として握り潰しているケースです。
この場合、ユーザー側には「何度試しても同じ見え方」になります。

## 5. なぜ「計画だけ」になったのか

エージェントは次の依存順で回答を組み立てます。

1. 計画（ユーザー可視）
2. データ取得（ツール）
3. データ理解
4. 本文生成

今回 2 で停止したため、1 のみが可視化された形です。これはエージェントの推論失敗というより、
**入力データ供給経路（ツール I/O）の障害に起因する未完了** と評価できます。

## 6. 再発防止のための改善提案

### 6.1 ツール実行基盤（優先度: 高）

- `Success` かつ空ボディ時は即座に `tool_output_empty` として明示的エラー化する。
- `No response received` の内部原因（timeout / parse / transport）を分類して返す。
- 同一エラー連続時に指数バックオフ＋フォールバック（別 API / 直接 read）を強制。

### 6.2 エージェント挙動（優先度: 高）

- 同一ツールが 2〜3 回連続で空応答なら、無限再試行を止めて障害報告モードに切替える。
- ユーザーへ「現在読み込めている情報」「不足情報」「次善策（手動貼り付け依頼等）」を即時提示する。
- `refs/` の存在のみ確認できた段階で、ファイル名をユーザーに再確認する分岐を追加する。

### 6.3 可観測性（優先度: 中）

- 1 リクエスト単位で `request_id` を表示し、サーバーログ追跡を可能にする。
- ツールごとに「送信サイズ / 受信サイズ / デコード成否」をメトリクス化する。
- UI 側で「成功（データあり）」と「成功（データなし）」を視覚的に区別する。

## 7. ユーザー影響

- 期待アウトプット（発表原稿）が得られない。
- 同一操作の反復により時間を消費する。
- 「モデルが考えていない」のではなく「資料を受け取れていない」問題が見えにくい。

## 8. 結論

本件は、**ツール連携経路の空レスポンス障害が主因** であり、計画だけ返る挙動はその二次症状です。
短期的には「空レスポンスの明示エラー化」と「再試行打ち切りルール」を導入し、
中期的には I/O 可観測性を強化することで、同種障害の切り分け時間を大幅に短縮できます。
