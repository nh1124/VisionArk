# VisionArk Native App 統合設計レポート (v2)

## 0. 背景と狙い
これまでの「Web中心・Native補助（常駐パネルのみ）」の設計を見直し、以下の2点を中核とした新しいNative Appの設計を定義します。
1. **現在のWeb Frontと同等のフル機能を持つNative版**の提供
2. **ローカル環境を直接操作・中継するための実行プロセス（Daemon）**の統合

これにより、ユーザーはブラウザに依存せず、OSに最適化された一つの強力なデスクトップアプリから「プロジェクト管理・対話」と「ローカルPCの自動操作」をシームレスに体験できるようになります。

---

## 1. 機能要件

### 1.1 Web Frontと同等のネイティブUI（メイン機能）
Native Appを起動した際のメインウィンドウとして、既存のWebポータルと完全な機能パリティ（同等性）を持たせます。
- **チャットワークスペース**: AIエージェントへの指示、思考プロセスの可視化（Thinking Process）、Activityの確認。
- **プロジェクト管理**: タスクの確認・作成、ノート（Global/Project）の閲覧・編集。
- **ダッシュボード**: ローカルおよびクラウドリソースの稼働状況モニタリング。
- **承認センター**: Native特有の高リスク操作（ファイル削除コマンド実行、決済アクション等）に対する明確な承認インターフェース。

### 1.2 ローカル操作の中継（Local Relay / Daemon）機能
AIエージェントがユーザーのローカル環境へ干渉・操作するための「手」となる機能です。
- **OSコマンド・スクリプト実行**: エージェントの指示に基づいてビルド（build）、テスト、スクリプト実行を行い、標準出力をサーバーに返す。
- **ファイルシステム操作**: プロジェクトフォルダの走査（Indexing）、コードファイルの読み書き、成果物の生成。
- **コンテキストの自動取得**: アクティブなウィンドウやユーザー作業の状況を受動的にフックし、タスク予測や自動記録の材料として提供する（※プライバシー保護のためオプトイン式）。

## 2. UI 設計

### 2.1 メインウィンドウ（フル・インターフェース）
- 左サイドバー（階層ナビゲーション）、メインコンテンツ（チャット/ダッシュボード）、右サイドバー（コンテキスト・Activity）という現在親しんでいる構成をNativeウィンドウで描画します。
- Tauri や Electron などの技術を用います。Web版（`core/frontend`）と機能面では同等を維持しつつ、実装は完全にコピー・分離し、Native特有のファイルドラッグ＆ドロップやOSショートカットに最適化した独自UIとして構築します。

### 2.2 常駐UI（システムトレイ ＆ ミニウィンドウ）
- メインウィンドウを閉じた後もプロセスは常駐し、タスクバーやメニューバーのアイコンから稼働状況を監視可能です。
- エージェントからの緊急の承認要求や、ローカルスクリプトの実行完了時には、OSネイティブの通知（Toast Notifications）と小さなポップアップパネルを表示します。

### 2.3 OSネイティブダイアログとの統合
- ローカル環境の機密ファイルやディレクトリをエージェントへ読み込ませる際の「フォルダ選択ダイアログ」など、OSネイティブのピッカー機能を活用します。

## 3. 変更スコープ（アーキテクチャ）

今回の設計変更により、システムアーキテクチャは以下の構成に進化します。

- **Native Frontend (独立した専用UIレイヤー)**:
  - 既存のWeb実装を直接参照（流用）することは避け、ファイルをコピーする形でNativeアプリのUIを構築します。これにより、Web側とNative側で依存性を排除し、互いのアップデートによる予期せぬ破壊や制約を防ぎます。
- **Native Backend (Rust/Node)**:
  - Tauriの場合はRustで、アプリ本体（ウィンドウ管理）とローカルコマンド実行（Daemon）を担当します。
  - OSとのインターフェース（IPC通信）の口を開け、Web UI側から「エージェントへのローカル操作権限の付与」を行えるようにします。
- **Cloud Backend (既存API)**:
  - データの正本（Task, Note, Job状態）は引き続き一元集約します。Native Appは定期的にCloud/LocalのBackendと同期し、ローカル中継の実行結果を送信します。

## 4. エージェントがコーディングに必要な情報

開発を行うエージェント（AI）が参照すべき技術要件とディレクトリ構造です。

### 4.1 ディレクトリ構成方針
```text
VisionArk/
├── core/
│   ├── backend/        # クラウド側のAPI・状態管理 (FastAPI等)
│   ├── frontend/       # Web版のReact UIコンポーネント (Next.js)
│   └── native/
│       ├── desktop/    # [推奨] TauriベースのNative統合基盤
│       │   ├── src/    # Rustバックエンド (Daemon / IPC等)
│       │   │   ├── main.rs      # エントリポイント・ウィンドウ管理
│       │   │   ├── commands.rs  # Frontendと連携するIPCコマンド群 (ファイル操作など)
│       │   │   └── daemon.rs    # バックグラウンドのローカル命令中継処理
│       │   ├── ui/     # Native専用のフロントエンド実装（Web版からコピー・独立管理）
│       │   └── tauri.conf.json
```

### 4.2 コアコンポーネント間の通信プロトコル（IPC）
Native UIに対して、Rust側（Tauri）から以下のIPCコマンドを公開し、Agentのツールとしてブリッジします。
1. **`execute_local_command(cmd, args, cwd)`**:
   - エージェントから指示されたCUIコマンドの実行とその標準出力を返すAPI。
2. **`read_local_file(path)` / `write_local_file(path, content)`**:
   - エージェントのコード修正やファイル要約のためのファイルI/O機能。
3. **`poll_agent_jobs(agent_id)`**:
   - サーバー上のエージェントが「ローカルPCでの実行要求」を出していないかの定期確認ワーカー。

### 4.3 開発ステップ・留意点
1. **ステップ1**: 既存の `core/frontend` から必要なUIソースコードを `core/native/desktop/ui/` へコピーし、完全に独立したデスクトップアプリのUIとしてビルド環境を整える。
2. **ステップ2**: Rust 側に `daemon.rs` を実装し、手動でテスト用のOSコマンドをローカル環境で実行できるかを確認する。
3. **ステップ3**: クラウドのAI推論時に実行されるツールリクエストをNative側に中継させ、実際のローカルファイル操作・コマンド実行を連動させるBridgeモデルを完成させる。
