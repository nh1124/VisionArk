# ファイル管理システム設計報告書 (v2)

## 1. 概要
VisionArkのファイル管理システムは、従来の「相対パスベース」から、堅牢でスケーラブルな**「UUID主体のレジストリモデル」**へと刷新されました。これにより、ファイルの移動、リネーム、重複への耐性が向上し、エージェントによる一貫した操作が可能になっています。

## 2. コアアーキテクチャ
システムは「データベース・レジストリ」と「物理ストレージ」の同期によって構成されています。

### A. UUIDレジストリ (`UploadedFile` テーブル)
すべてのファイルとディレクトリは、データベース上の `UploadedFile` モデルによって管理されます。
- **ID (UUID)**: 外部公開される一意の識別子。すべてのAPI操作はこのIDを主体に行われます。
- **filename**: ユーザーに見える論理パス（例: `refs/manual.pdf`）。フォルダ構成の表現に使用されます。
- **is_directory**: フォルダであるかどうかを示すフラグ。フォルダも独自のUUIDを持ちます。
- **storage_path**: ディスク上の物理的な場所。アップロードされたファイルは衝突を避けるため UUID名で保存されます。

### B. 階層構造ディレクトリ
プロジェクトは以下の標準ディレクトリをサポートしています：
- `refs/`: 参照用ドキュメント（不変）。
- `artifacts/`: AIによって生成された成果物。
- `files/`: ユーザーのアップロードファイル。
- `notes/`: ユーザーまたはエージェントによる動的なメモ。

## 3. 主要な操作フロー

### ファイルの保存・作成
- **Project-Centric Creation**: フロントエンドやエージェントは、複雑な相対パスを意識せずに、`project_id` と `directory` (種類) を指定するだけでファイルを保存できます。
- **自動同期**: ファイルが保存されると、バックエンドの `FileService.sync_project_directory` が実行され、データベースに即座に登録されます。

### UUIDによる操作 (Unification)
以下の操作はすべて **論理パスではなく UUID** を使用して行われます：
- **閲覧 (Open)**: `/api/files/content/{uuid}` を介して内容を取得。
- **ダウンロード**: `/api/files/download/{uuid}` を介して取得。フォルダの場合はZIPアーカイブが自動生成されます。
- **削除 (Recursive Delete)**: `/api/files/{uuid}` で削除。フォルダを削除した場合、その配下の全ファイル・サブフォルダがデータベースとディスクの両方から再帰的に削除されます。

## 4. 特徴と利点

- **物理操作からの独立**: ディスク上の物理ファイル名がUUIDであっても、DBが論理的なファイル名を管理するため、ユーザー体験を損なわずに安全性（重複回避）を確保できます。
- **直接操作への追従 (Git Sync)**: Git操作などでディスクの内容が直接書き換えられた場合でも、定期的なスキャン同期によってDBが自動更新され、新しいファイルには自動的にUUIDが割り振られます。
- **一貫したAPI**: ファイルの種類に関わらず、同一のIDベースAPIで操作可能なため、エージェントのツール利用が簡略化されます。

## 5. プロジェクト・ガバナンスと規則
VisionArkではプロジェクトごとに、ファイル命名規則や必須メタデータ、自動アーカイブのライフサイクルを定義できます。

- **`.visionark/project_rules.json`**: プロジェクトごとのガバナンスルールのソースオブトゥルース（隠し設定ファイル）。
- **Ruler Node による自動化**: 設定されたルールに基づき、ファイルの自動整理、インデックス更新、アーカイブが実行されます。
- **専用ツール**: `get_project_rules` と `update_project_rules` を介して安全に管理されます。
